# User Profile Builder

负责建立及后续更新一对有界的当前协作视图：`USER.md` 描述用户，`SOUL.md` 描述 Agent。更新可以由用户直接提出，也可以由已有维护流程按需复用。普通个人简介、人物模仿与完整工作区配置由相应能力处理。

## 1. 确定范围

从请求和当前配置解析目标目录、语言与模式：创建、更新、审查、拆分或对齐。路径无法确定时先澄清。默认采用 OpenClaw 兼容的文件分工；平台未说明时在交付中标明假设。

目标文件已存在且本轮有修改需求时，进入更新模式，以原文为基线。按文件契约的“更新触发与差异”区分实际更新、待确认候选和无变化；只有明确要求只检查时才以审查模式结束。

读取目标中已有的两份文件，以及相关 `IDENTITY.md`、`AGENTS.md`；画像放在子目录时也读取所属工作区规则。读取 [文件契约](references/file-contract.md)，它是内容归属、证据、隐私和存量维护的权威规则。

完成条件：明确哪些文件可写、哪些只作为上下文。审查模式只返回问题；用户已授权修改且目标清楚时直接推进。迁移到其他文件、外发或同步需有相应授权。

## 2. 提取行为证据

在工作草稿中按文件契约区分已确认、推断与未知，并为每条候选信息说明它会改变哪种回答、判断或行动。证据账本只服务本轮，不自动生成持久文件。

已有材料足够时进入下一步；缺少关键协作信息时读取 [访谈指南](references/interview-guide.md)，按相应深度提问并达到其停止线。局部更新只补齐本轮变更所需证据。

完成条件：每条拟新增或改变的用户事实有依据；未确认内容保留在交付说明中，模板空白按需省略。

## 3. 整理当前视图

按文件契约的“存量维护与容量”处理现有内容，再加入新证据。新建时按需读取 [USER 模板](assets/USER.md.template) 与 [SOUL 模板](assets/SOUL.md.template)，只使用有内容的章节。

用可观察的行为表述偏好和原则，例如“先给结论，再给依据”。将分支细节放到已授权的按需资料，用带触发条件的指针连接。

完成条件：每条存量内容都有保留、合并、替换、移除或迁移的处理结果；仅有新价值的内容进入正文。同样的证据再次输入时不改正文、日期或增加记录。

## 4. 审查与验证

读取 [成对评审](references/evaluation-rubric.md)，检查完整文件对。先在临时目录中准备候选 `USER.md`、`SOUL.md`；未修改的一份使用原文副本。用本 skill 目录中的脚本检查候选：

```bash
python3 <skill-dir>/scripts/validate_pair.py <candidate-dir> --json
```

`<skill-dir>` 替换为本 skill 实际安装目录，`<candidate-dir>` 为候选目录。预算参数和默认值通过脚本 `--help` 查询；预算选择遵循文件契约。

修复所有 `ERROR`。对每项 `WARNING` 修正问题或给出具体保留理由；脚本仅检查机械问题，语义判断按成对评审完成。审查模式在这里交付发现，不写入目标。

完成条件：候选满足全部评审项，或明确列出阻塞原因；有阻塞时交付草稿与具体取舍，不标记完成，不覆盖目标。

## 5. 写入与交付

候选通过后，只写入授权范围内实际变化的文件。覆盖前确保有可恢复的版本或临时副本；写入前若目标已被其他操作改变，重新读取并合并本轮变更。保留与本轮无关的有效内容，按同一预算复验落盘文件。

交付文件路径、两份文件各自的字符数与预算、验证结果及简短变更摘要。摘要说明新增、替换和清退的原因，以及尚未确认的信息、未完成的迁移或保留警告；无变化时说明无变化。
