# 搭建与检查

## 盘点与布局

盘点库根全部 `.md`，包括隐藏目录、日记、模板、系统规则和画像。记录无法读取、外部符号链接或受应用管理的文件，避免递归到库外；这些缺口不能从全库完成报告中消失。附件保持原位。

复用用户当前结构，以下只用于缺少相应位置时：

```text
知识库/
  AGENTS.md
  index.md
  log.md
  系统/
    index.md
    规则/
      index.md
      知识库维护.md
      笔记属性.md
    个人画像/
      index.md
      USER.md
      SOUL.md
  ...用户内容目录/
    index.md
    ...笔记.md
```

确定实际规则目录、画像位置、维护规则与属性规则文件名，随后各模板都使用这些位置。已有功能相同的规则就合并，不生成第二套；再次运行先重新发现用户调整后的路径。

首次批量修改前保存本次涉及文件的可恢复版本和原路径清单；备份放库外，避免再次纳入知识扫描。Git 库也要覆盖当前未提交内容，不把已有提交误当成全部备份。只读检查不生成备份或日志。

## 落成库内规则

- 将 [维护模板](../assets/maintenance.md.template) 写为实际维护规则。`property_rule_path`、`log_path`、`user_path`、`soul_path` 均解析成相对于该规则文件的真实路径。
- 将 [属性规则](property-rules.md) 写为实际属性规则，补 `type: Rule`。把其中 `SPEC.md#...` 链接改为 [来源记录](spec-source.md) 中固定提交的官方 Spec URL，保留章节锚点；规则不得引用开发仓库或已安装 Skill 的本机绝对路径。现有库内若已有同版本规范副本，可以复用其实际链接。
- 完整规范原文留在本 Skill 的 `references/SPEC.md`。普通维护依据库内规则，新增陌生字段或规范升级时再读取对应条文；无法取得条文时报告未核实项，不臆造格式。
- 两份画像由入口指定的画像能力创建在实际位置，再依据属性规则检查格式。传入库根的既有协作指令；画像目录不是一个新工作区，不在其中另外生成 `AGENTS.md` 或另一对画像。

规则需要的字段说明和维护动作必须实际落盘，仅写“请遵循 OKF”或只指向 Skill 名称不算完成。

## 既有内容与保留文件名

原正文和有效 YAML 属性保持原意，按 [属性规则](property-rules.md) 补齐实际需要的字段。YAML 无法解析时先定位原错误，不用整份重写丢失内容。

`index.md` 若承载文章、仪表盘或规则正文，先保存为有意义且不冲突的普通笔记，修正原入链和锚点语义，再建立目录索引。`log.md` 若含其他正文，同样先保留；已有真实历史继续保留。无法无损确定去向时列出具体冲突，先处理其他文件。

保留现有 Wiki 链接、块引用、嵌入和插件功能。按 Obsidian 实际解析或唯一目标路径检查入链；同名文件不能只靠 basename 匹配。修改路径时同步索引、入链、出链、来源路径和规则指针，不在代码示例中全局替换。使用标准链接的新入口和规则优先采用相对路径，并处理空格等字符。

全库采用 OKF 结构与保留 Obsidian 扩展分别报告；不得把“YAML 合规”说成“所有语法跨工具等价”。应用管理文件、动态模板等无法安全修改时列为未完成项，不为了格式改应用配置或删除功能。

## 索引与日志

索引格式查 [Spec §8](SPEC.md#8-index-files)。为每个含知识笔记的目录及其必要祖先建立 `index.md`，列本层笔记和下一级内容目录，可附准确的简短说明；已有 `description` 可复用，没有则从内容概括，不因此强加属性。规则索引的说明写清各规则的适用情境。

根索引只做逐级导航，并声明目标版本 `okf_version: "0.2"`；子索引不加 frontmatter。纯附件目录不强制索引，父索引可以指向它。保留已有分组和有用说明，更新遗漏、失效或重复条目。索引不列自身，不把下层全部笔记灌进根索引。

日志格式查 [Spec §9](SPEC.md#9-log-files)。根 `log.md` 按真实的 `YYYY-MM-DD` 分组，新日期在前；一次任务合并一条，说明改了什么、为什么改，并链接受影响笔记。重要新增、删除、移动、结论／规则／画像修订需要记录；错字、排版和无变化的重复检查不产生新条目。保留旧历史，不用初始化文本覆盖已有日志。已有子目录日志保留，但不再批量生成重复日志。

## 验收

1. 对比前后清单，每个原文件有去向；无未说明的内容丢失、覆盖或迁移。全库目标文件均纳入结果，无法处理的逐项列明。
2. 用 YAML 解析器检查普通笔记的 `type` 和实际选用字段；索引、日志分别按其格式检查，不套普通笔记模板。结构合规依据 [Spec §11](SPEC.md#11-conformance)。
3. 将各目录内容与索引逐一比对；验证本次新增、变更链接和锚点，区分既有缺失知识与本次引入的断链。验证日志日期和旧历史仍在。
4. 从 `AGENTS.md` 沿指针能到达真实的两份画像、规则索引、维护规则和属性规则；复制到库内的规则链接不依赖开发机路径。
5. 核对正文、链接和嵌入的保留情况。可使用 Obsidian 时抽查受影响功能；只有文件检查时如实说明未做应用内验证。

交付实际修改范围、检查结果、备份位置及未处理项。只读检查不写入；用户手动编辑在下一次相关维护或显式检查时补齐，不承诺后台监听。
